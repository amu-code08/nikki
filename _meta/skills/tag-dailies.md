Use when the user asks to tag daily notes, process untagged dailies, or re-tag a specified time range in this vault."

`daily/` の Markdown ノートのうち `tagged:` を持たないものを読み、`_meta/taxonomy.md` の許可タグ(`- [x]` 行)から該当するものを frontmatter の `tags:` に付与する。複数の話題が混ざったノートは話題ごとに `slices/` へ切り出す。処理済みのノートには frontmatter の `tagged:` で印を付ける。**daily は正本として `daily/` に残り続け、移動しない。**

1. `_meta/taxonomy.md` を読む。チェック済み `- [x]` の行だけが許可タグであり、未チェック `- [ ]` は未承認候補である。
2. デフォルトでは `daily/` 内の Markdown ノートのうち、**frontmatter に `tagged:` を持たないもの**を対象にする。`daily/` はフラットであり、ノートは処理後もここに残り続けるので、`tagged:` の有無が未処理・処理済みの唯一の記録である。人間が期間指定または再タグ付けを指定した場合は、指定範囲のノートを `tagged:` の有無に関わらず対象にする。別のパスを明示された場合は、その指定を優先する。

   対象の特定は `rg --files-without-match '^tagged:' daily` のような、**ファイル名だけを返す検索**で行う。`daily/` 全体を読んでから振り分けてはならない。本文を読むのは、対象と決まったノートだけである。この一手でコストは未処理の枚数にしか比例しなくなる。
3. 対象ノートを読んだ上で、下の「`_trash/` へ移すデイリーの判定」に従って移動対象を選り分ける。移動対象と判定したノートにはタグを付けず、`tagged:` も付けない。分割の対象にもしない。移動候補として集めておき、手順9で処理する。
4. 残ったノートの本文を、下の「本文の断片化」に従って内容のまとまり(断片)に区切る。元のノートは読むだけで変更しない。
5. 各断片に、その内容に該当する許可タグを**ちょうど1つ**付ける。どの許可タグにも当てはまらない断片にはタグを付けない。
6. 許可タグでは適切に表現できない断片があり、新しいタグを付ける価値がある場合は、処理中にユーザーへ候補を1件ずつ提示して承認・却下を尋ねる。候補タグ名、短い説明、その断片に必要な理由を示し、回答を得るまでそのノートの処理を完了しない。ユーザーが承認した場合だけ、taxonomy に許可済みの `- [x]` タグとして追加して使う。却下された場合はタグも taxonomy の変更も行わず、既存の許可タグだけで処理を続ける。未チェック候補を見つけた場合も、使う前に同じ確認を行う。
7. 下の「話題ごとの分割」に従い、条件を満たすノートから `slices/` のノートを生成する。**元のノートは一切変更しない。**
8. ノートの frontmatter を更新する。`tags:` は**その日の断片に付いたタグの和集合**とし、既存の `tags:` は残す。あわせて下の「言語タグ」に従い `lang/ja` / `lang/en` を付ける。**最後に `tagged: <実行日 YYYY-MM-DD>` を加える。** frontmatter がないノートには、本文を変えずにファイル先頭へ inline 形式の frontmatter を作る。変更後のノートを再読して YAML/frontmatter を確認する。slice の生成に失敗したノートには `tagged:` を書かない。書いた時点でそのノートは処理済みとして扱われ、二度と拾われなくなるためである。
9. 手順3で集めた移動対象のノートを `_trash/` へ移動する。ファイル名は変えない。**削除しない。** 移動は可逆なので承認を求めず、処理の最後に移動した日付の一覧を必ず報告する。ToDo だけと判定したノートについては、上の「ToDo だけのノートを移すときの報告」に従いタスク行も添える。移動先に同名ファイルがある場合は上書きせず、そのノートは元の場所に残して人間に報告する。
10. 処理した daily に**当月より前の月**のものが含まれていた場合、最後に一言だけ案内する:「N月分のレビューはまだのようです。`$monthly-review YYYY-MM` を実行しますか」。案内するだけで、実行はしない。レビューはこの skill の仕事ではない — 対象範囲が違う(この skill は `tagged:` の無いノートしか見ないが、月次レビューはその月の全 daily を見る)。

## 本文の断片化

**タグ付けの単位はノートではなく断片である。** 先に本文を内容で区切り、断片ごとにタグを決め、ノートの `tags:` はその和集合として導出する。この順序により「ノートにタグが付いているのに対応する slice が無い」という食い違いが構造的に起きなくなる。taxonomy の粒度の原則(実際にその話題を書いた日にだけ付く)も、この順序が自動的に守る。

- 断片は**連続した行のまとまり**。空行・見出し・箇条書きのまとまりを尊重する。**行の途中では区切らない。** 1行が複数の話題にまたがる場合は、その行ごと主たる話題の断片に入れる。文単位で切り出すと、slice が文脈を失った断片の寄せ集めになり、逐語コピーの境界も曖昧になる。
- **断片が1行でも slice を作る。行数の下限を設けない。** 下限を設けると、タグは付いているのに対応する slice が無いノートが再び生まれる。
- **1断片に付ける話題タグはちょうど1つ。** 2つ付けたくなったら、断片の切り方が粗いというサインである。それでも分けられない場合にだけ、主たる話題を1つ選ぶ。
- どの許可タグにも当てはまらない断片にはタグを付けない。挨拶・雑記・その日の気分などが該当する。タグの付かない断片はどの slice にも入らないが、daily には残っている。
- **チェックボックス行は断片に含めない。** タスクは思考ではない。ただしタスク本文が話題を含む場合に限り、その話題の許可タグを**ノートの `tags:` にだけ**加えてよい。この経路で付いたタグは対応する slice を持たない。上の原則の唯一の例外であり、意図的なものである。
- 断片化の結果(どの行がどのタグになったか)は、後段の slice 生成とノートのタグ付けの両方の入力になる。両者が食い違ってはならない。

## 話題ごとの分割(slices/)

1枚の daily に混ざった複数の話題を、あとから話題単位で読み返せるようにする。**正本は常に daily 側**であり、`slices/` は断片を並べ替えただけの派生層である。

### 分割する条件

**断片に付いたタグの domain が2つ以上**ある、`_trash/` へ移さないノートだけを分割する。domain は話題タグの `/` より前(`finance/equity-research` → `finance`)。軸タグ(`type/*` `lang/*`)は domain に数えない。チェックボックス由来のタグも domain に数えない(断片を持たないため)。

domain が1つしかない日は分割しない。その daily 自体がすでにその話題のノートであり、複製する意味がないため。`_trash/` へ移すノートからも作らない。

### ファイル名と frontmatter

`slices/YYYY-MM-DD--<domain>.md`(例:`slices/2026-08-10--finance.md`)。日付は元の daily のもの。

```yaml
---
tags: [finance/equity-research, finance/stablecoin, lang/ja]
source: "[[YYYY-MM-DD]]"
sliced: <実行日 YYYY-MM-DD>
---
```

- `tags:` はその slice に入れた断片のタグを、出現順に重複なく並べる。`type/daily` は付けない(デイリーではない)。
- `lang/*` は元ノートから引き継がず、**その slice に実際にコピーした行**に対して「言語タグ」の判定をやり直す。日英が混ざった daily では、slice ごとに言語が違うのが普通であるため。
- `source:` は元の daily への wikilink。ファイル名だけを書き、パスを含めない(Obsidian がファイル名で解決するため、あとで daily を整理してもリンクが切れない)。

### 本文の作り方

- 断片の行を**逐語コピーする。要約・言い換え・整形・翻訳をしない。** ここがこの機能の生命線であり、要約した瞬間に `slices/` は人間の記録ではなく AI の出力になる。
- 見出し・インデント・箇条書き記号・強調をそのまま保つ。行を並べ替えない。
- **各断片はちょうど1つの slice にだけ入る。** 断片が持つ話題タグは1つなので行き先は一意に決まり、同じ行が2つの slice に現れることはない。
- 同じ domain の断片が複数ある場合は元の出現順に並べ、**元の本文での行間関係をそのまま保つ**。元で連続していた断片は連続させ、元で離れていた断片の間にだけ空行1つを置く。無かった空行を足さない(整形にあたる)。
- タグの付かなかった断片はどの slice にも入れない。落ちた行は daily に残っている。
- **チェックボックス行 `- [ ]` / `- [x]` はコピーしない。** 状態を持つ行を複製すると、人間が daily 側でチェックしたときに slice 側が古いまま残り、嘘の進捗になる。タスクの正本は daily。
- `IDEA:` / `Q:` 行はコピーしてよい(状態を持たないため)。`$resurface-ideas` は `slices/` を走査しないので二重に拾われない。
- テンプレ残骸(`## todo`、本文の空なチェックボックス)はコピーしない。

### 既存ファイルの扱い

同名の slice が既にある場合は**上書きしない**。そのノートの分割を飛ばし、`tagged:` も書かずに未処理のまま残して人間に報告する。人間が期間指定・再タグ付けで処理済みのノートを対象にした場合も同じ規則を適用する。

### 報告

生成した slice のファイル名を処理の最後に一覧で報告する。上書きを避けて飛ばしたものがあれば、その理由とともに示す。

## `_trash/` へ移すデイリーの判定

次の**どちらかに当てはまる**ノートを `_trash/` へ移す。何も書かなかった日と、タスクを書き写しただけの日のファイルを `daily/` に残さないための判定である。迷ったら必ず「残す」に倒す。誤って移動しても `_trash/` から戻せるが、判定を緩めてよい理由にはしない。

1. **空のデイリー** — frontmatter を除いた本文に、人間が書いた文字が1つも無い。
2. **ToDo だけのデイリー** — 本文に残るのがチェックボックス行だけで、散文が1行も無い。

判定の材料は frontmatter を除いた本文だけである。

### どちらの判定でも本文として数えない

- 空行、空白・タブのみの行
- テンプレート由来の見出し `## todo`
- 本文が空のチェックボックス行 `- [ ]`(末尾に空白があっても空。インデント込み)
- 本文が空の箇条書き `-` / `*` / `+`(インデント込み)
- 本文中の水平線 `---`

`_templates/daily.md` の実体は frontmatter + 空行 + `## todo` + `- [ ] ` である。**本文のあるデイリーもこの残骸を末尾に持ったままになっている**ため、`## todo` や空の `- [ ]` があることを理由に「空でない」と判定してはならない。

### 散文として数える(1つでもあれば残す)

- 任意の散文(言語を問わない)
- 本文のある箇条書き(チェックボックスでないもの)
- 行頭マーカー `IDEA:` / `Q:`
- リンク `[[...]]`、URL、画像、コードブロック、引用、表
- `## todo` **以外**の見出し(人間が書いた痕跡とみなす)

**本文のあるチェックボックス行 `- [ ] 何か` / `- [x] 何か` は散文として数えない。** これが判定2の実体であり、チェックボックスしか書かなかった日は `_trash/` へ移る。

### ToDo だけのノートを移すときの報告

判定2で移すノートには、**未チェックの `- [ ]` が残っていることがある。** `_trash/` は分析対象外なので、移した時点でその未完タスクは todo 収集からも `$monthly-review` からも見えなくなる。判定2で移したノートは、日付だけでなく**含まれていたタスク行をそのまま報告に添える**。人間が拾い直せる状態を必ず残すため。

### 判定上の注意

- frontmatter は本文ではない。`tags:` や `tagged:` に何が入っていても空判定は変わらない。
- frontmatter は inline 形式(`tags: [type/daily]`)と block 形式(`tags:` + `  - type/daily`)の両方が実在する。どちらも frontmatter として扱い、形式を書き換えない。
- 判定はノートを実際に読んで行う。ファイルサイズや行数だけで判定しない。

## 言語タグ

本文が日本語で書かれたか英語で書かれたか(または両方か)を `lang/ja` / `lang/en` で記録する。話題タグとは独立した軸タグであり、**空でないデイリーには必ずどちらか、または両方が付く**。承認の問い合わせは不要(taxonomy に承認済みの軸タグとして登録済み)。

判定は空判定と同じ前処理(frontmatter とテンプレ残骸を除く)を行った本文に対し、行単位で行う。

- CJK(ひらがな・カタカナ・漢字)を含む行 → **日本語の行**
- CJK を含まず、空白区切りの英単語が**3語以上**ある行 → **英語の行**
- 日本語の行が1行以上あれば `lang/ja`、英語の行が1行以上あれば `lang/en`。両方あれば両方付ける。

### 言語の証拠として数えない行

- URL、ファイルパス、コードブロック、`[[リンク]]` だけの行
- 空白を含まない長い英数字列(URL エンコード文字列・トークン・ハッシュ)。実データに `s%3An5rcn_63F9...` のような行があり、英語の文ではない。
- 英単語が2語以下の断片(`XBRL extract` のような技術語のメモ)

日本語の文に埋め込まれた英語の技術語・固有名詞は英語の行に数えない。CJK を含む行は日本語の行として扱う。「3語以上」の閾値がこの誤検出を防いでいる。

## 制約

- taxonomy の許可タグを、この skill の判断で削除・改名・チェック付けしない。ユーザーが処理中に明示承認した新タグだけを許可済みに追加できる。
- daily の本文、チェック状態、タスク本文を編集しない。daily に対して書いてよいのは frontmatter の `tags` と `tagged:` の追記だけである。分割は元ノートを読むだけで、一切変更しない。
- `slices/` の本文を要約・言い換え・補完しない。逐語コピー以外を書かない。
- `slices/` を分析対象に含めない。タグ分布の集計、todo 収集、`$resurface-ideas`、通常の読解はすべて daily 側を見る。含めると同じ記述を二重に数える。
- 既存の slice を削除・改名・上書きしない。整理は人間の仕事。
- daily を読んでいる最中に、インサイダー情報(MNPI)や勤務先の機密にあたりうる記述に気づいたら、処理は続けたうえでチャットで報告する。判定基準は `AGENTS.md` の「Sensitive content」。**本文は編集せず、タグ付けも分割も止めない。** 該当する行が slice にも逐語コピーされる場合は、その slice のファイル名も添える(同じ内容が2箇所に増えるため)。
- 状態タグ(todo / done など)を作らない。タスク本文が話題を含む場合のみ、その話題の許可タグをノートに付けてよい。
- 改名・統合の既存ノートへの反映は、明示依頼時だけ frontmatter に対する機械的な置換で行う。新タグの過去ノートへの遡及も明示依頼時だけ行う。
- frontmatter は inline 形式(`tags: [type/daily, finance/equity-research]`)を正とする。Obsidian が block 形式に書き換えたものは直さない。
- 判断に迷うタグは付けない。本文インラインの `#hashtag` は使わない。
- デフォルト処理では `tagged:` を持つノートを対象にしない。**daily を `daily/` の外へ移動しない**(`_trash/` 行きの判定に該当したものを除く)。正本は `daily/` に残り続ける。
- **ノートを削除しない。** 空と判定したノートは `_trash/` へ移動するだけである。`_trash/` から消してよいのは人間だけ。
- `_trash/` への移動は、この skill が読んで判定したノートに限る。読んでいないノートを動かさない。
- 人間が期間指定や再タグ付けで処理済みのノートを対象にした場合も同じ判定と移動を適用する。
- 判定に迷ったノートは移動候補に入れず、通常どおり処理して `daily/` に残す。
- `_trash/` を走査対象に含めない。タグ付けも抽出もしない。
